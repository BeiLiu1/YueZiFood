# 悦子吃什么：产品与技术设计

## 1. 目标与原则

“悦子吃什么”是一套面向情侣日常点餐的私人应用。普通用户通过 iPhone PWA 浏览已上架内容、组合点单和提交未上架菜品需求；管理员通过手机接收提醒，通过 PC 管理用户、分类、菜品、食材、食谱、订单和新菜需求。

第一版遵循以下原则：

- 无需 Mac、无需 App Store，通过 Safari 添加到主屏幕。
- 开发和部署尽量简单，采用单仓库、单应用、单数据库文件。
- 数据模型正规，不把账号或业务数据写死在代码中。
- 仅实现当前两类角色和核心业务闭环，不建设通用权限平台。
- 移动端俏皮有趣，PC 管理端清晰高效。

## 2. 用户与角色

系统固定两种系统角色：

- `ADMIN`：可进入移动端管理员视图和 PC 管理端，维护全部业务数据并处理订单、需求。
- `USER`：可浏览菜单、点单、提交新菜需求、查看自己的订单和需求。

角色记录保存在数据库中，不允许删除或新增其他角色。管理员可维护用户、启停用户、重置密码和分配角色。

首次启动时：

- 初始化 `ADMIN` 和 `USER` 两条角色记录。
- 根据环境变量初始化一个管理员用户。
- 初始管理员用户名和密码不写入源码或镜像。
- 密码使用强哈希保存，登录成功后使用安全 Cookie 保持会话。

## 3. 第一版功能范围

### 3.1 iPhone PWA

- 用户名和密码登录、退出登录。
- 首页展示一级分类和推荐内容。
- 最多两级分类浏览，支持搜索菜品。
- 菜品详情展示图片、简介、分类、预计耗时和可选备注。
- 一次选择多道菜形成一张订单。
- 提交时选择用餐日期、餐次（早餐、午餐、晚餐、夜宵）并填写可选备注。
- 查看订单列表、订单详情和状态变化。
- 在待确认状态取消自己的订单。
- 提交未上架菜品需求：菜名、描述、期望日期、可选参考图片。
- 查看新菜需求状态和管理员回复。
- 添加到主屏幕、开启推送通知、查看应用内通知。

管理员登录移动端后额外拥有：

- 查看待处理订单和需求。
- 查看订单合并食材清单及各菜品食谱。
- 快速接受、拒绝、开始准备或完成订单。

### 3.2 PC 管理端

- 工作台：今日/近期订单、待处理需求、菜品与分类统计。
- 用户管理：新增、编辑、启停、重置密码、分配系统角色。
- 分类管理：分类树、新增、编辑、启停、排序、关联菜品查看。
- 菜品管理：草稿、上架、下架、图片、简介、分类、食材、食谱。
- 食材管理：名称、默认单位、备注和引用情况。
- 食谱管理：步骤排序、用量、时间和操作说明。
- 订单管理：筛选、详情、状态处理、拒绝原因、食材汇总。
- 新菜需求管理：研究笔记、接受/拒绝、转为菜品草稿、关联最终菜品。
- 通知记录：查看发送结果，不提供复杂营销通知功能。

### 3.3 明确不做

- App Store、原生 iOS 安装包和 Android 原生包。
- 开放注册、短信/邮箱验证码、社交账号登录和找回密码。
- 通用菜单权限、按钮权限和自定义角色。
- 在线支付、库存、采购订单、营养分析、公开分享和社交功能。
- 多租户和家庭空间隔离。

## 4. 分类设计

- 分类最多两级，通过 `parent_id` 表达父子关系。
- 一级分类用于大类，例如菜品、饮品、甜品、水果。
- 二级分类用于细分，例如家常菜、汤羹、咖啡、果汁。
- 菜品与分类为多对多关系，同一菜品可同时属于多个分类。
- 分类包含名称、图标、排序、启用状态。
- 禁止创建第三级分类。
- 已有关联菜品或子分类的分类不可直接删除；应先解除关联，或将分类停用。
- 停用分类不在移动端展示，但不影响历史订单。

## 5. 核心业务流程

### 5.1 已上架菜品点单

1. 用户按分类或搜索浏览已上架菜品。
2. 用户将一道或多道菜加入本次点单。
3. 用户选择用餐日期、餐次并填写可选备注。
4. 系统创建订单和菜品快照，状态为 `PENDING`。
5. 系统写入应用内通知，并尝试向管理员发送 Web Push。
6. 管理员查看订单、合并食材清单和每道菜食谱。
7. 管理员接受订单后，订单依次进入 `ACCEPTED`、`PREPARING`、`COMPLETED`。
8. 管理员也可在待确认阶段拒绝订单并填写原因。
9. 用户可在待确认阶段取消订单。
10. 每次有效状态变化均写入状态历史，并通知下单用户。

订单状态：

- `PENDING`：待确认。
- `ACCEPTED`：已接受。
- `PREPARING`：准备中。
- `COMPLETED`：已完成。
- `REJECTED`：管理员已拒绝。
- `CANCELLED`：用户已取消。

### 5.2 未上架菜品需求

1. 用户提交菜名、描述、期望日期和可选参考图片。
2. 系统创建 `PENDING` 需求并通知管理员。
3. 管理员记录研究笔记并将需求标记为 `RESEARCHING`。
4. 管理员接受需求时，系统创建关联菜品草稿。
5. 管理员补齐分类、图片、食材和食谱后发布菜品。
6. 菜品发布后需求自动进入 `PUBLISHED`，用户收到“新菜解锁”通知。
7. 管理员也可拒绝需求并填写原因，需求进入 `REJECTED`。

需求状态：`PENDING`、`RESEARCHING`、`ACCEPTED`、`PUBLISHED`、`REJECTED`。

## 6. 食材与食谱规则

- 食材作为独立主数据维护，避免同一种食材被重复创建。
- 食材包含名称、默认单位和备注；名称在有效数据中唯一。
- 菜品通过关联表记录食材用量、单位和准备说明。
- 数量允许为空，用于“适量”“少许”等无法精确量化的内容。
- 订单食材汇总按“食材 + 单位”合并；不同单位不做自动换算。
- 汇总结果同时保留来源菜品，方便管理员核对。
- 每道菜使用一份当前食谱，包含按顺序排列的步骤。
- 菜品修改不会反向修改历史订单中的菜名快照，但管理员查看制作资料时默认使用当前有效食谱。

## 7. 页面与路由

### 7.1 公共页面

- `/login`：登录。
- `/install`：PWA 安装和通知开启引导。

### 7.2 用户移动端

- `/`：首页和一级分类。
- `/category/:id`：分类菜品。
- `/dish/:id`：菜品详情。
- `/cart`：本次点单。
- `/orders`、`/orders/:id`：订单列表与详情。
- `/requests`、`/requests/new`、`/requests/:id`：新菜需求。
- `/notifications`：应用内通知。
- `/profile`：账号信息、修改密码、通知设置。

### 7.3 管理端

- `/admin`：工作台。
- `/admin/users`：用户管理。
- `/admin/categories`：分类管理。
- `/admin/dishes`：菜品管理。
- `/admin/ingredients`：食材管理。
- `/admin/orders`：订单管理。
- `/admin/requests`：新菜需求管理。
- `/admin/notifications`：通知记录。

服务端对所有 `/admin` 页面和管理 API 再次校验 `ADMIN` 角色，不能只依赖前端隐藏入口。

## 8. 数据模型

主要数据表：

- `roles`：角色编码、名称、系统角色标记。
- `users`：用户名、显示名、密码哈希、状态、最后登录时间。
- `user_roles`：用户与角色关联。
- `categories`：父分类、名称、图标、排序、状态。
- `dishes`：名称、简介、封面路径、预计耗时、发布状态。
- `dish_categories`：菜品与分类关联。
- `ingredients`：名称、默认单位、备注、状态。
- `dish_ingredients`：菜品、食材、数量、单位、准备说明、排序。
- `recipe_steps`：菜品、步骤序号、标题、说明、预计分钟数。
- `orders`：下单用户、用餐日期、餐次、备注、状态、拒绝原因。
- `order_items`：订单、菜品、菜品名称快照、数量。
- `order_status_history`：订单、原状态、新状态、操作者、说明、时间。
- `dish_requests`：发起用户、菜名、描述、期望日期、图片、状态、回复、研究笔记、关联菜品。
- `notifications`：接收用户、类型、标题、正文、业务类型、业务 ID、已读时间。
- `push_subscriptions`：用户、设备标识、Push Endpoint、密钥、最后成功时间、状态。

所有业务表使用不可变主键，并记录创建时间和更新时间。删除优先采用状态停用；订单、需求、通知和状态历史不做物理删除。

## 9. 技术架构

采用 Nuxt 4 全栈单体：

- Vue 3 + TypeScript 实现移动端 PWA 和 PC 管理端。
- Nuxt Server API 实现认证和业务接口。
- Tailwind CSS 实现定制视觉，不引入重量级后台模板。
- Drizzle ORM 管理 SQLite 表结构和迁移。
- SQLite 使用 WAL 模式，数据库文件挂载到持久化目录。
- 菜品与需求图片保存在持久化上传目录，数据库仅保存相对路径和元数据。
- Service Worker 提供 PWA 安装、基础静态资源缓存和 Web Push。
- Docker 构建应用；Caddy 负责域名、HTTPS、反向代理和上传大小限制。

仓库保持单应用结构，前端组件、服务端业务模块和共享类型分区组织。业务模块之间通过服务接口协作，页面不得直接访问数据库。

## 10. 视觉与交互

移动端采用已确认的“薄荷便当社”方向：

- 主色为薄荷绿，搭配黄色和粉色强调色。
- 深色描边、轻微错位阴影、贴纸和便当格元素。
- 文案采用任务式、轻松且亲密的语气，例如“选出今晚的快乐来源”。
- 成功点单、状态变化和新菜发布使用轻量动画，不阻塞操作。
- 拒绝、错误和安全提示保持温和但明确，不用玩笑掩盖重要信息。
- 支持减少动态效果设置，保证文字对比度和点击区域可访问性。

PC 管理端沿用配色和品牌元素，但减少装饰、提高信息密度，表格和表单优先保证效率。

## 11. 通知设计

通知触发：

- 新订单提交：通知所有启用的管理员。
- 新菜需求提交：通知所有启用的管理员。
- 订单状态变化：通知下单用户。
- 新菜需求状态变化或发布：通知发起用户。

通知采用“应用内记录优先、Web Push 增强”的策略：

- 业务事务先保存订单/需求和应用内通知。
- Web Push 在事务完成后发送。
- 推送失败不回滚业务数据。
- 失效订阅自动停用，管理员可查看发送失败记录。
- 用户必须先将 PWA 添加到主屏幕，再通过明确按钮授权通知。

## 12. 错误处理与安全

- 输入在前端提供即时提示，服务端执行最终校验。
- 登录失败返回统一提示，不泄露用户名是否存在。
- Cookie 使用 `HttpOnly`、`Secure`、`SameSite=Lax`；生产环境仅允许 HTTPS。
- 修改密码后撤销该用户现有会话。
- 文件上传限制为 JPEG、PNG、WebP，校验真实内容类型和文件大小，使用随机文件名。
- 所有状态变更在服务端校验合法前置状态，防止重复点击和越级修改。
- 创建订单时使用事务，确保订单、订单项、历史和应用内通知一致。
- 管理端危险操作采用二次确认；系统角色、历史订单和历史需求不可删除。
- 日志记录请求标识、用户、业务对象和错误摘要，不记录密码、Cookie 或 Push 密钥。
- 对登录和写接口进行基础频率限制。

## 13. 缓存与离线策略

- 缓存应用壳、图标和必要静态资源。
- 菜单列表采用网络优先并使用短期缓存作为弱网回退。
- 登录、点单、订单处理和管理操作必须在线完成。
- 第一版不实现离线下单队列，避免重复订单和状态冲突。
- 新版本激活时提示用户刷新，不在填写表单过程中强制刷新。

## 14. 部署与备份

生产部署：公网服务器 + Docker Compose + Caddy。

- Caddy 监听 80/443，并为购买后的域名自动申请和续期证书。
- Nuxt 应用仅暴露给 Caddy，不直接暴露应用端口。
- 挂载 `data/` 保存 SQLite，挂载 `uploads/` 保存图片。
- 环境变量保存会话密钥、初始管理员信息和 Web Push VAPID 密钥。
- 每日备份 SQLite 和上传目录，保留最近 7 份日备份和 4 份周备份。
- 发布前自动执行数据库迁移；迁移失败则不启动新版本。
- 回滚时恢复上一镜像；涉及不可逆迁移时同时恢复对应备份。

开发阶段可通过本机或公网 IP 的 HTTP 地址验证大多数业务功能；PWA 推送和最终安装验收在域名 HTTPS 配置后执行。

## 15. 测试策略

- 单元测试：状态机、分类层级限制、食材汇总、权限判断、密码与会话工具。
- API 集成测试：登录、用户管理、分类、菜品、订单、需求和通知事务。
- 组件测试：分类导航、购物车、订单状态、管理表单。
- 端到端测试：用户登录并点单、管理员处理订单、用户提交新菜需求、管理员发布新菜。
- PWA 真机验收：两台 iPhone 添加到主屏幕、保持登录、接收 Web Push、点击通知进入正确详情。
- 部署验收：HTTPS、持久化卷、备份恢复、镜像重启后数据不丢失。

## 16. 分阶段实施

### 阶段 1：基础骨架

Nuxt、数据库迁移、初始化角色和管理员、登录、布局、基础测试、Docker 开发环境。

### 阶段 2：菜单资料管理

分类、食材、菜品、图片、食谱，以及移动端分类浏览和搜索。

### 阶段 3：点单闭环

多菜购物车、订单、食材汇总、状态机、移动端与 PC 订单页面、应用内通知。

### 阶段 4：新菜需求闭环

需求提交、研究处理、转菜品草稿、发布关联和结果通知。

### 阶段 5：PWA 与部署

Manifest、Service Worker、Web Push、Caddy HTTPS、备份脚本、两台 iPhone 安装验收。

## 17. 第一版验收标准

- 管理员可登录 PC 端并创建普通用户。
- 管理员可维护最多两级分类，菜品可绑定多个分类。
- 管理员可维护菜品图片、食材用量和有序食谱步骤并上架。
- 普通用户可在 iPhone 上按分类浏览并一次选择多道菜。
- 用户可指定日期、餐次和备注并成功提交订单。
- 管理员可看到合并食材清单和各菜品食谱，并完成合法状态流转。
- 用户可取消待确认订单，并能看到订单历史和拒绝原因。
- 用户可提交未上架菜品需求，管理员可研究、拒绝或转为菜品并发布。
- 应用内通知始终记录；域名 HTTPS 配好后，两台 iPhone 能收到对应 Web Push。
- PWA 可从 Safari 添加到主屏幕并以独立窗口运行。
- 容器重启后数据库和图片不丢失，备份可成功恢复。
